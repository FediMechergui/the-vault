# API and stream contract

Gateway: HTTPS `:8443`. All JSON responses use UTF-8. Browser preview CORS defaults to localhost/127.0.0.1 port 8080; set `ALLOWED_ORIGINS` explicitly for another preview origin.

## Credentials

Account creation requires `{pseudo, consent: true}` and returns a management JWT. It allows that account's enrollment, configuration and deletion, but never vault access. The mobile client stores it in platform secure storage.

Authentication starts with an account UUID. It returns a random session ID and random session token, valid for at most ten minutes. Session secrets are sent in the first WebSocket JSON message or `X-Session-Token` for the decision endpoint; they do not appear in WebSocket URLs.

Only passing **every** server-selected layer yields a 15-minute vault JWT. Token issuer, audience, scope, expiry and continued account existence are checked. Signing keys are generated by bootstrap. A vault JWT cannot enroll templates; a management JWT cannot read the meme.

## WebSocket

Connect to `/ws/stream/{session_id}` and immediately send:

```json
{"token":"the-session-token"}
```

The server sends `ready` and the current challenge. Binary camera frames are:

| Offset | Size | Encoding |
| --- | --- | --- |
| 0 | 4 bytes | unsigned frame number, big-endian, increasing |
| 4 | 8 bytes | timestamp in milliseconds, big-endian, increasing |
| 12 | remainder | JPEG, normally quality 70, 640×480 or portrait equivalent |

Maximum WebSocket message: 300,000 bytes. Decoded dimensions are checked before OpenCV allocation. One in-flight frame per Flutter client limits queueing. The server limits frame rate, capture length and samples; clients receive `tracking`, `dropped`, or `error`. The session determines the layer: a client cannot choose a different layer by changing a frame.

`tracking` includes quality, current gesture label, normalized landmarks, server processing latency, sample count and liveness/air-signature state. The client calculates round-trip latency separately. Gesture labels are geometric/blendshape classifications, while authentication compares the full enrolled time series.

For face authentication, follow the randomized liveness prompt first. It is not part of the secret-expression template. Then:

1. After the local three-second countdown, send `{"type":"begin"}`.
2. Wait for `capturing`, continue binary frames.
3. For hand captures, start with an open hand. A pinch rising edge starts tracing, release allows points to enter the trace, and a second pinch completes it.
4. Send `{"type":"finish"}` at the capture deadline or completed hand trace.
5. Receive `captured` with repetition progress, or `quality_error` and retry the same repetition.
6. Enrollment commits only when the required 2/3/5 repetitions are present. Authentication calls `/next`, which returns `next`, `failed`, or `unlocked`.

Three failed **matching** attempts lock the account for five minutes. Poor capture quality asks for another capture and does not count as an impostor match. Successful completion resets the failure counter. New auth sessions invalidate older sessions for that account; replaying a consumed session cannot issue another token.

## Internal services

`contracts/vision.proto`: `Extract(Frame) → Landmarks`, `Health`, `Release`. JPEG bytes travel only to the vision service. Extracted signals, never JPEGs, go to `/enroll/{layer}` or `/score/{layer}` on the scoring service. Scoring responses contain the actual `engine` identifier.

Redis stores transient landmarks/session state with a ten-minute maximum lifetime and disabled disk persistence. PostgreSQL stores AES-256-GCM ciphertext with per-record random nonces and user/layer associated data. MinIO stores the meme. Signed media is proxied through the gateway so MinIO does not need a public port.

The calibration thresholds and simple liveness rules require real volunteer evaluation. They are not a defense against all video replay, injected camera streams or sophisticated spoofing.
